MISSION_AND_TECHNICAL_NOTE — 약지기 - 진화형 복약 관리

참가자(데이콘 닉네임): SDH · SCPC 2026 예선 2차 본 문서는 T+48에 동결된 Mission 선언 「약지기 - 진화형 복약 관리」의 용어·범위·인과관계를 그대로 승계하며, 앱·소스·증거에서 확인 가능한 사실만 서술한다. 점수·통과 여부·판정값은 운영 채점 체계가 산출하는 것으로, 이 문서와 앱은 이를 추정·출력하지 않는다.

의료·안전 고지. 약지기는 의료 조언·진단·복약 지시가 아니다. 앱은 용량·복용 여부를 스스로 정하지 않으며, 판정 기준은 "기록된 의사 지시의 최신 버전·기한·중단 scope"라는 사실이고 앱은 이를 기억·대조해 표시할 뿐이다. 복용은 항상 사용자의 최종확인으로만 확정된다(버튼명도 행위 통제가 아닌 "복용 기록"이다). 등장하는 사용자 페르소나 "대혁"(71세, 1인 가구)과 처방·조제·배송·복용 기록·메모 등 건강 데이터 일체는 실존 인물·실제 환자 데이터와 무관한 완전 합성 데이터이며, 실제 의료기관·약국·계정·결제는 사용하지 않고 모든 산출물은 앱 내부 draft/preview로만 존재한다. 이 고지는 앱 첫 화면 최상단에도 표기된다.

1. Mission 요약

대상 사용자·문제. 만성 처방(혈압약 상시)과 단기 처방(이번 주만 항생제)을 함께 복용하는 합성 노인 페르소나 대혁이, 아침·저녁 복용 세션마다 오늘 먹을 약 목록·수량을 확인하고 잔량을 관리한다. 복약 도구의 실패는 세 방향이다 — [반복] 매번 처음부터 다시 묻거나, 반대로 지난 체크리스트를 통째로 재사용해 만료된 단기약·중단된 약이 유령처럼 재등장함, [중단] 확인 도중 프로세스 종료·중복·역순 이벤트로 기록이 사라지거나 이중 기재됨, [변화] 처방 정정·복용 중단·권한 회수가 온 날에도 과거 방식을 밀어붙임. 본질은 "어떤 기억이 지금도 유효한지 판별하고, 무효가 된 부분만 고치는 것"이다.

반복되는 사용자 결과(성공상태). 매 세션 "확인된 복용 체크리스트"(유효성 판정을 통과한 처방, 잔량 반영)가 생성·확정되는 것이며, 성공상태와 근거는 화면과 원장(ledger)에서 관찰된다.

장기 목표(여러 session 뒤 확인). 선언 문면을 그대로 승계한다: episode가 반복될수록 ① 직전 같은 유형 대비 불필요한 입력·재확인 단계가 감소하되 복용 전 최종확인·권한·삭제 확인은 유지되고, ② 잘못된 재사용(만료 단기약 재등장, 정정 전 지시 재표시, 삭제 원문 부활)이 게이트에 차단되어 claim-off 대비 관찰 가능하게 감소하며(목표치 0건, 발생 시 원장에 감지·기록 후 최소 범위 복구), ③ 처방·상황·권한 변화 시 질문·대기·보류·재계획·중단을 근거와 함께 선택하고, ④ 정정·중단 시 영향받은 기억 성분(그 약의 알림 예약·리필 대기·파생 추론)만 되돌리며, ⑤ 리필 draft의 지연 도착(가상시간)이 이후 세션의 잔량 판단에 실제 반영되고, ⑥ 강제 종료·중복·역순 이벤트에도 원장의 commit 경계 기준으로 복용 기록 이중 기재·삭제 부활을 감지·해소하도록 reconcile되는(목표치·복구 원칙은 ②와 동일) — 세션과 프로세스 재실행을 넘어 이어지는 진화하는 복용 체크리스트를 유지한다.

Primary value. 안전한 재사용(trustworthy reuse) 한 가지: 지금도 유효한 처방 기억만 재사용해 확인 부담을 줄이되, 무효 기억의 재사용을 차단한다. 확인 감소와 안전은 별개 기능이 아니라 하나의 유효조건 원장(동일한 유효성 판정) 위에서 달성되는 한 가치의 두 측면이다.

2. E1→E2→E3→E4 인과 사슬 — 앱 화면에서의 실증

앱 화면은 섹션별로 이 사슬을 그대로 조작·관찰하게 구성된다. 아래 버튼명은 실제 화면 문구다.

  • E1 Learn — "학습 (E1 — 사실·추론·기한형 구분)" 섹션. [혈압약 처방 등록 (지시 v1 · 잔량 6 · 임계 5) — 상시]는 처방 내용을 FACT(약 단위 지시 버전 bp_v1이 권위)로, 잔량·임계는 지시와 무관한 권위 중립 사실로 분리 기록한다. [항생제 등록 (7일 기한 …) — 기한형]은 EPHEMERAL·기한형(TERM)으로 valid_until과 함께 기록된다. [민감 진단 메모 기억 (합성)]은 삭제·tombstone 시연 대상이다. 각 기억에는 유효조건(약별 지시 버전·기한·중단 scope·권한 상태)과 출처 이벤트가 원장에 남으며, 이 분류가 이후 모든 재사용·판단·복구 범위를 결정하는 원인이 된다.
  • E2 Reuse — "오늘의 복용 세션" 섹션. [복용 세션 시작 — 유효한 처방만 프리필]은 유효조건을 통과한 기억만으로 오늘 체크리스트를 프리필한다(만료·중단·소모 항목은 게이트가 제외). 복용 전 최종확인은 생략되지 않는다 — 체크박스 확인이 별도 이벤트로 원장에 기재된 뒤에야 [복용 기록] 버튼이 열리고, 기록 1회당 해당 약의 잔량 정수가 1 감산된다. 잔량이 기록된 임계치 아래로 내려가면 리필 draft가 생성되고, [리필 draft 승인] 후 가상시간이 경과하면 준비완료 도착이 다음 세션의 잔량·프리필을 실제로 바꾼다(6절).
  • E3 Exception — "상황 변화 (E3 예외 → E4 복구)" 섹션. [처방 정정 v2], [항생제 복용 중단], [민감 메모 삭제], [네트워크 온/오프 전환], 중복 전달·역순 도착이 저장된 방식과 충돌하면, 유효조건 매칭으로 영향 항목을 특정해 질문(ASK)·대기(WAIT)·보류(ABSTAIN)·재계획·중단 중 하나를 근거와 함께 선택한다. 예: 오프라인에서 전송 성격 결정은 정직하게 WAIT, 배우자 약([배우자 약에 대한 결정 요청])은 관리 대상이 아니므로 ABSTAIN.
  • E4 Recover. 정정·중단 시 출처 링크를 역추적해 영향받은 성분(그 약의 알림 예약, 미도착 리필 대기의 취소, 파생 추론의 무효화)만 되돌리고 다른 약의 유효한 학습은 보존하며, 복구된 체크리스트로 다음 세션이 정상 진행된다.

session 경계와 downstream 인과 변화(두 지점 이상). 세션 경계는 [새 세션 시작]·[반나절 전진]으로 명시 전환되며, 앞 episode의 선택이 뒤 episode에서 최소 세 지점을 실제로 바꾼다: ① 프리필 내용(만료 항생제·중단 약은 다음 세션 목록에서 제외되고 화면에 "목록 제외"로 표시), ② 가능한 행동(등재되지 않은 약은 복용 기록 대상에서 빠짐), ③ 도착 결과 반영(승인된 리필 draft만 이후 세션 잔량에 가산됨). 세 변화 모두 화면과 evidence/ export에서 관찰된다.

3. Signature mechanism — VG-Ledger(Validity-Gate Ledger)

3.1 구조

기억 하나마다 다음을 기록한다.

  • 유형: FACT(처방 내용 등 사실) / INFERENCE(복용 확인 시각에서 결정론적으로 파생된 "잘 지켜지는 시간대" 등, derived_from 출처 링크 보유) / EPHEMERAL(일회성 ONE_OFF — 첫 사용 후 소모, 기한형 TERM — 기한 내 세션마다 재사용·기한 경과 시 만료)
  • 유효조건: 약별 지시 버전(entity별 권위 map — 항생제 정정이 혈압약 기억을 기각하지 않는다), 기한(valid_until, ISO 문자열 비교로 결정론 판정), 중단 scope, 권한 상태
  • 출처 링크: 생성 이벤트 ID(origin_event)와 파생 근거(derived_from) — 복구 시 역추적 경로
  • 삭제 tombstone: 삭제 시 원문은 제거되고 값 없는 ID만 남아 어떤 경로에서도 원문이 부활하지 않는다

3.2 게이트 3지점 — 하나의 유효성 판정 공유

선언 문면대로, 재사용·충돌·복구 세 지점이 하나의 유효성 판정(권위·기한·scope·소모 기준)을 공유한다.

  1. 재사용 게이트(REQUEST_DECISION): 유효하고 현재 대상 약에 연결된 기억만 최소 context로 선택 — distractor(배우자 약) 기억은 선택되지 않는다.
  2. 충돌 게이트(CORRECT_FACT/REVOKE_SCOPE): 새 권위·철회 scope와 유효조건이 어긋나는 항목만 정밀 특정해 무효화.
  3. 복구 게이트: 무효화된 근거의 파생 항목을 출처 링크로 전이적으로 함께 무효화하고, 영향 약의 미도착 리필 대기를 취소(원장에 CANCELLED_PENDING 기재), 나머지는 보존.

함수 수준의 사실은 다음과 같다: 재사용 게이트와 UI 체크리스트 조립이 같은 isValid 판정 함수를 직접 호출하며(ChebiCore.validMemories — 유효성 판정이 화면용/시험용 두 곳으로 갈라질 수 없는 단일화 지점), 충돌·복구 게이트는 동일한 기준(구권위만 무효화하는 권위 비교, 철회 scope 매칭, 출처 링크 역추적)을 무효화 방향으로 대칭 적용한다.

3.3 CII 인과 기여 논증

문제 claim: 유효성 판정 없는 재사용은 만료·정정 전·중단 기억을 되살려, 확인 감소가 안전 훼손으로 바뀐다. 효과 claim: 게이트가 있으면 무효 재사용이 차단되고 영향 특정 복구가 가능하다. 이 claim은 다음 이유로 인과적으로 검증 가능한 형태다: (a) 게이트는 gateEnabled 단일 스위치로만 on/off 되는 최소 구조라 비교의 조작 변수가 하나뿐이고, (b) 앱 내 짝비교 실험실이 각 충돌 이벤트의 실제 영향 집합(ground truth)을 데이터로 명기해 지표가 자의적 해석이 아니며, (c) 기한 만료·리필 도착은 가상시간 며칠 뒤에야 드러나는 후반 전이(late-horizon) 지표라 초반 화면만으로 흉내낼 수 없다. 선언한 지표 — 세션당 입력·재확인 단계 수, 잘못된 재사용 건수, 영향 특정 정확도, 복구 보존율 — 는 비교 리포트 필드(s3_prefill/s7_prefill_final, s5_expired_ghost_reuse, s6_impact_precision, s6_preservation_rate)와 1:1 대응한다. 이때 프리필 계열 지표는 두 가지로 정직하게 구분된다: 비교 리포트의 s3_prefill/s7_prefill_final은 결정 게이트가 선택한 context 크기(selected_context_ids 개수 — 격리 arm의 관찰값)이고, 6절의 세션 프리필 수는 evidence/ui/metrics.json에 기록되는 화면 단위 관찰값(슬롯 등재 행 수 + 이번 세션 도착 반영 수)으로, 정의가 서로 다르며 각각의 자리에서 집계된다. 알려진 실패 경계도 명시한다: 권위 중립으로 기록된 기억(잔량·임계)은 설계상 지시 정정의 영향 밖이며(정정이 잔량 이력을 지우면 안 되기 때문), 게이트의 이득은 유효조건이 기록된 기억에 한정된다 — 유효조건 없이 저장된 값은 보수적 STABLE로 남는다.

4. Comparison mode — full vs claim-off 정의

  • 같은 시작 snapshot: [비교 실행] 시점의 라이브 상태를 복제한 뒤, 두 arm 모두 격리 공간 내부에서 RESET 후 동일 시나리오를 시작해 ground truth가 라이브 이력과 무관한 결정론이 되게 한다.
  • 같은 이벤트 열: 두 arm은 S0(RESET)~S7의 동일한 8단계 이벤트 열(이벤트로 세면 10건 — 학습이 2약×각 2건: 학습 → 첫 세션 → 3일 경과·기한 만료 → 만료 후 결정 → 처방 정정 v1→v2 → 정정 후 세션)을 같은 가상시각·같은 순서로 실행한다. mechanism on/off 외 UI·model·seed·이벤트 열·quota·network 조건은 동일하다.
  • 격리 저장공간: full arm은 namespace medkeeper-cmp-full, claim-off arm은 medkeeper-cmp-off의 서로 분리된 저장소를 사용하며, 라이브 원장(medkeeper-core-full)과도 격리되어 한쪽의 저장·삭제·Reset이 다른 쪽에 보이지 않는다.
  • claim-off의 정의: 같은 APK·같은 core에서 유효성 게이트 판정만 비활성화한 동일 코드경로의 기본 동작 — 살아있는 기억의 통짜 재사용(권위·기한·scope·소모 판정 없음), 충돌 시 대상 전체 무효화(전체 재확인), 정정 시 전체 재작성. claim-off arm도 기능이 망가진 허수아비가 아니라, 직전 상태를 보수적으로 통째 재사용하고 충돌 시 전체 재확인으로 폴백하며 전 episode를 정상 완주한다.

비교 리포트는 ground truth(정정의 실제 영향 집합)를 데이터로 명기하고 — 보존 대상 집합은 복구 보존율(s6_preservation_rate) 산식의 기준으로 내장된다 — 두 arm의 관찰값과 함께 화면에 표시되며 evidence/comparison/comparison_run.json으로 내보내진다.

5. 아키텍처와 상태 모델

5.1 단일 core — UI와 Probe의 production parity

핵심은 ChebiCore 하나다: 기억 원장 + 행동 원장 + 보류 결과 큐를 가진 영속 상태 위에서 13개 operation을 결정론적으로 실행한다. 도메인 파사드(MedDomain)는 UI 버튼 행동을 합성 이벤트(ProbeInputStep)로 만들어 Probe와 같은 core.execute()에 넣는다 — UI 전용 판단 로직이 없으므로 "UI와 Probe가 같은 production core"라는 요건이 코드 경로 수준에서 성립하며, SOURCE에 포함된 테스트(SameAdapterPathTest, UiFlowReplayTest 등)가 public UI와 protected 경로가 같은 candidate adapter를 호출함을 보인다. UI 원장과 Probe 실행은 동일 namespace(medkeeper-core-full)를 공유한다.

5.2 현재 권위·삭제·부분 복구 규칙

  • 현재 권위: 권위는 전역 단일값이 아닌 entity(약)별 map이다. 정정(v1→v2)은 그 약의 구권위 기억과 그 파생 추론만 무효화하고, 권위 중립 기억(잔량·도착 이력)과 다른 약은 영향 밖이다.
  • 삭제·tombstone: DELETE는 원문을 제거하고 값 없는 ID만 tombstone에 남긴다. entity 전체 삭제는 그 약의 미도착 대기·미완 행동도 함께 취소한다. 역순 재전달로 삭제 원문이 돌아와도 reconcile 게이트가 REJECTED_TOMBSTONED로 기각한다(상태 무변형·기각 기록만 추가). 사용자의 명시적 재학습만 새 인스턴스로 허용된다 — 부활이 아니라 새 출처의 새 기억이다.
  • 부분 복구: 철회 scope에 걸린 항목 + 그 파생(전이 폐쇄)만 무효화하고 나머지는 preserved_state_ids로 명시 보존한다. 영향 약의 미도착 리필 대기는 취소되어 원장에 남고, 해당 미완(PROPOSED) 행동은 CANCELLED로 종결된다.

5.3 기한만 정정(UNTIL-only)의 대칭 의미론

정정의 원칙은 "값이 오면 기한을 승계하고, 기한이 오면 값을 승계한다" — 어느 한쪽만 정정돼도 다른 쪽이 조용히 유실되지 않는다.

  • 값 동반 정정: 새 기한이 없으면 기존 인스턴스의 valid_until을 승계한다(연장 지시 없이 값만 바뀐 처방이 기한을 잃지 않음).
  • 기한만 정정(연장·단축): 대상 약의 기한 보유 기억을 기존 값 그대로 새 기한으로 재기록한다. 같은 step에 새 지시(권위 정정)가 동반되면, 방금 그 정정으로 무효화된 기한 보유 기억도 새 권위로 인수해 재기록한다 — "새 지시로 기한 변경"이 값 대체 없이 와도 유실되지 않는다.
  • 기한 보유 기억이 전무하면: 기한 없이 학습된 기한형(TERM)에 새 기한을 신규 부여한다 — 기한형이 기한 없는 채 영구 재사용되는 침묵 no-op을 막는다.

5.4 CORE-1…6 대응 위치

CORE 약지기에서의 위치

6. CORE-6 본질성 — 지연 결과가 복약 도메인의 본질인 이유, 프리필 지표 정의

복약에서 "리필"은 본질적으로 지연 사건이다: 잔량 부족의 인지(이번 세션), 리필 요청의 승인(사용자 확정), 준비완료의 도착(며칠 뒤)이 서로 다른 시점에 일어나고, 도착 전까지의 모든 세션 판단은 "도착 안 됨"을 전제로 내려져야 한다. 약지기에서 이 사슬은 장식이 아니라 상태 기계다 — 리필 승인 → 가상시간 경과 → 도착이 다음 세션의 잔량·프리필 판단을 실제로 바꾼다: ① 복용 기록으로 잔량이 임계 아래로 내려가면 리필 draft가 생성되고, ② [리필 draft 승인]만이 리필 도착 대기(outcome-decl 경로)의 등록 트리거이며 잔량 가산은 그 리필 도착 기억에만 반응한다 — draft 생성 결정 자체도 일반 지연 결과를 원장에 남기지만(행동 기록·commit 경계용), 이는 잔량에 가산되지 않는 별개 경로다, ③ [3일 전진] 후 도착 판정을 통과한 결과만 outcome 원장으로 이동해 도착 기억(권위 중립 FACT, 등록 시점의 약에 귀속)을 만들고 해당 행동이 PROPOSED→COMMITTED로 승격되며, ④ 다음 [복용 세션 시작]이 이 도착을 잔량에 가산(+30)해 프리필 수와 리필 필요 판단이 도착 전과 달라진다. 같은 도착은 1회만 가산되고, 중단·삭제된 약의 도착은 잔량을 오염시키지 않는다(미도착 대기는 중단 시점에 이미 취소). 이 전 과정이 행동·결과를 순서대로 남긴 원장(evidence/ledger/outcomes.json)과 화면 잔량 표기로 대조된다.

프리필 지표 정의(선언 정합). 세션 프리필 수 = 이번 슬롯(아침/저녁)에 등재된 체크리스트 행 수 + 이번 세션에 새로 잔량에 반영된 도착 수. 이는 REQUEST_DECISION 응답의 selected_context_ids 개수가 아니다 — selected는 판단에 쓰인 기억 ID 집합이고, 프리필 지표는 사용자 확인 부담을 재는 화면 단위 관찰값이므로 별도로 정의·집계한다(직접확인 수 = 등재되지 않았지만 잔량 기록이 남은 행 수). 비교 리포트의 s3_prefill/s7_prefill_final(선택 context 크기)과의 구분은 3.3절에 명시했다.

7. 예외·장애 시 예상 상태

  • process 강제 종료·재실행: 상태는 매 step 커밋되므로 kill 시점과 무관하게 relaunch 후 원장에서 무손실 복구된다. 증명은 해시 체인이다 — 직전 step의 state_after_sha256과 재실행 후 첫 step의 state_before_sha256이 일치하고, process_epoch 증가가 그 step의 변화로 기록된다. 결정-도착 사이에 kill이 와도 행동은 PROPOSED로 남아 완료로 위장되지 않는다(상태 정직성).
  • 중복·역순 이벤트: 중복 재전달(REPLAY)은 새 행동을 만들지 않고 동일 행동을 반환하며(복용 기록 이중 기재 차단), 라벨은 행동 원장 상태와 1:1이다(커밋 완료 CONFIRMED_COMPLETE / 결과 미도착 PENDING / 취소 ABSTAIN). 역순 도착(DELIVER_OUT_OF_ORDER)은 tombstone·권위 게이트 심사로 기각 사유를 분리 기록하고 기억 원장은 무변형이다.
  • network 단절: 로컬 판단(체크리스트 확인·복용 기록)은 오프라인에서도 진행된다. 전송 성격 결정(리필 draft)만 정직한 WAIT로 보류되고, 원본 이벤트 ID가 기록되어 연결 회복 후 [보류 결정 재전달]로 정확히 한 번 재시도된다(이벤트당 행동 최대 1개). 화면 문구가 이 이원화를 그대로 안내한다.
  • permission 거부·회수: 전 경로는 권한 없이 동작한다(화면 확인 모드). 회수 시 알림 scope 성분만 무효화되며(8절), 무효화된 성분은 재허용만으로 부활하지 않고 명시적 재등록으로만 복귀한다 — tombstone·부활 금지 원칙과 일관된다.

8. Mobile 필연성

8.1 mobile constraint — POST_NOTIFICATIONS 실권한 경로

주 제약은 알림 권한의 거부·중도 회수다. Android 13+(targetSdk 35)의 실제 OS runtime permission POST_NOTIFICATIONS를 [알림 권한 요청 (OS 실제 권한)] 버튼으로 요청하며, 권한 상태는 유효조건의 실제 입력으로 취급된다: ① [복용 알림 예약]은 실권한이 허용된 때에만 호출되고 알림 경로 scope(scope_notify)로 기록된다. ② 사용자가 OS 설정에서 권한을 중도 회수하면 앱 복귀 시점(onResume)에 전이를 감지해 해당 scope 철회를 원장에 기재하고 알림 파생 성분(예약·파생 추론)만 무효화한다 — 다른 약 기억은 보존된다. ③ 재허용만으로는 철회 기록이 바뀌지 않는다 — 화면이 "알림 예약을 다시 등록해 주세요"로 안내하고, [복용 알림 예약]을 명시적으로 재등록하는 scope 재부여 학습이 철회 목록에서 그 scope를 제거하며 새 출처의 새 기억을 만든다. 회수로 무효화된 성분은 이 명시적 재등록으로만 복귀하고 자동 부활하지 않는다. Probe 경로의 합성 REVOKE_SCOPE 이벤트와 실권한 경로는 같은 core 연산으로 수렴하는 이원 설계다. 부 제약은 process 강제 종료·재실행 후 복용 원장·보류 질문·가상시각의 local continuity(7절)다.

8.2 PC counterfactual

상시 프로세스인 PC 대화창이 공짜로 얻는 연속성이 모바일에서는 설계 대상이다. PC로 옮기면 다음이 사라지거나 달라진다 — state: 프로세스 epoch·재실행 reconciliation·kill 전후 해시 연속성이라는 상태 자체가 성립하지 않는다(죽지 않는 프로세스에는 복구할 단절이 없다). decision: OS runtime permission 분기(회수→성분 무효화→재허용 후 명시적 재등록)와 오프라인 세션의 WAIT/로컬 진행 이원화라는 판단 분기가 사라진다. evidence: process_epoch 증가 기록, kill 경계를 넘는 해시 체인, 권한 전이의 원장 기재라는 증거 형태가 만들어질 수 없다. 복용이 침상·부엌·외출의 생활 동선 기기에서 일어난다는 사용 맥락까지 더해, 이 Mission의 검증 대상 행동은 모바일에서만 실재한다.

9. 이벤트-리모컨 = 제품화 경로

UI의 합성 이벤트 버튼들은 데모용 장식이 아니라, 실제 제품에서 실입력이 들어오는 지점을 손으로 앞당겨 재현하는 "리모컨"이다. 각 버튼과 실입력의 대응은 다음과 같다.

10. Probe Mode 연결과 검증 경로

  • 공개 점검 UI: 앱 하단 "공개 점검 (Probe rehearsal)" 섹션에 세 control이 있으며 정확한 accessibility content description을 가진다 — SCPC_PROBE_IMPORT(공개 입력 가져오기), SCPC_PROBE_RUN(공개 입력 실행), SCPC_PROBE_EXPORT(결과 내보내기). 입력 파일 위치(앱 외부 파일 폴더 경로)가 화면에 표시되고, import 오류·실행 결과·export 경로를 화면에 정직하게 표시한다.
  • 공개 연습도구·live 검증 실행 경로: 공개 연습은 Kit의 공식 Runner가, live 검증은 Dacon OPS가 protected component를 구동하며, 이 경로와 앱 내 공개 점검 UI가 모두 같은 candidate adapter 실행부(ChebiProbeAdapter.executeStep)를 경유한다. step 증거·receipt 실파일은 앱 외부 파일 폴더의 probe_evidence/에 결과에 신고된 ID와 1:1 파일명으로 기록된다.
  • production parity: public UI와 protected component는 같은 candidate adapter(ChebiProbeAdapter)를 거쳐 같은 ChebiCore·같은 namespace를 호출한다. 시험 전용 저장소·점수용 분기·pack 감지 표식은 없으며, SOURCE의 integration test가 두 진입경로의 동일 adapter 호출을 검증한다.
  • Judge가 evidence를 찾는 경로: [증거 내보내기 (evidence/*)] 버튼이 MISSION_ADAPTER.json의 evidence_path와 동일한 상대경로로 실파일을 기록한다 — 상태는 evidence/state/(current_goal·target_entity·context_selection·facts·authority·invalidation·recovery·tombstones), 원장은 evidence/ledger/outcomes.json(대기·도착·기각·행동), 세션 지표는 evidence/ui/metrics.json, 짝비교는 evidence/comparison/comparison_run.json. 화면 표기(체크리스트·잔량·기억 원장 열람·비교 요약)와 이 파일들은 같은 상태의 두 관찰이다.
  • 결과에 없는 것: 앱은 PASS/FAIL, relation outcome, anchor, 점수·합격선을 계산하거나 출력하지 않는다. 결과에는 step별 decision state, selected/invalidated/preserved ID, before/after 해시, 행동 멱등·commit·outcome, tombstone, evidence ID 등 관찰 가능한 구조화 사실만 담긴다.

11. 결정론 구현 신고 — model/backend/runtime

본 제출물은 AI model을 사용하지 않고, 참가자 관리 backend·원격 endpoint가 없으며, 모든 판단이 온디바이스 결정론 규칙으로 수행된다. 실시계·난수를 읽지 않고 가상시간과 입력 이벤트만으로 구동되며, 시간 판정은 ISO-8601 문자열 비교로 결정론적이다. 상태 digest는 재현 불가한 런타임 메타(process marker)를 제외하고 계산되므로 같은 입력이면 기기·프로세스 이력과 무관하게 같은 해시 체인이 나온다 — 이것이 결정론의 검증 가능한 형태다. 따라서 동결 대상 backend 배포본이 존재하지 않고, model 호출 수는 0으로 판단당 4회·run당 60회 상한과 60초 판단기한 안에 자명하게 들어오며(호출 수는 Runner가 기록하고 제출 완성 도구가 이관한다), 재시도 정책은 model 호출이 아닌 이벤트 수준(WAIT 이벤트의 1회 재전달, REPLAY의 멱등 echo)에만 존재한다. runtime freeze는 APK 자체의 동결로 완결된다.

12. 맺음 — 안전 경계의 재확인

약지기의 모든 "판단"은 기록된 의사 지시의 최신 버전·기한·중단 scope라는 사실과 현재 상태의 대조이며, 그 대조 결과의 표시다. 앱은 복용을 권하지도 막지도 않는다 — 만료·중단으로 목록에서 제외된 약은 "지시 없음(중단·만료)" 또는 "기록 없음 또는 중단·만료"로 사유와 함께 표시될 뿐이고, 등재된 약도 사용자의 최종확인 이벤트 없이는 복용 기록이 열리지 않는다. 이 경계(기억·대조·표시까지, 지시·결정은 하지 않음)는 선언 문면, 화면 문구, 코드 주석, 본 문서에 동일하게 고정되어 있으며, 모든 데이터는 완전 합성이다.
