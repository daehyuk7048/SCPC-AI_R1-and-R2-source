# 약지기 — CII 소유권(ownership) 브리핑 (제출물 아님 · 심층 검증 대비 내부 자료)

심층 검증에서 "구현을 이해·소유하고 있는가"를 확인하는 문답에 대비한 정리.
답변 원칙: 사실만, 코드 위치로, 한계는 먼저 말한다.

## A. 심사자가 발견할 수 있는 관찰 7건과 정답 (감사6 LOW 전량)

1. **권한 회수 후 앱 복귀 직후, 상단 메시지는 "무효화했습니다"인데 원장 배지가 아직 [유효]/[정지]로 보일 수 있다.**
   → 맞습니다. 복귀 렌더가 상태 스냅샷을 먼저 뜨고 권한 전이 이벤트를 그 뒤에 반영하기 때문에 1렌더 지연이 있습니다. 아무 버튼이나 한 번 누르면 갱신됩니다. 원장·증거 파일(exportEvidence)은 항상 신선한 스냅샷을 읽으므로 정확합니다. 가이드 §5에 "다음 조작 시 갱신"으로 명시했습니다.
2. **화면 회전 시 세션 UI가 초기화된다.**
   → UI 인메모리 상태(sessionActive 등)는 Activity 재생성에서 리셋되지만 원장은 영속입니다. 세션을 다시 시작하면 REQUEST_DECISION이 1건 더 기록될 뿐 상태 모순은 없습니다(자가 치유형). 보류(WAIT) 결정은 waited_events로 영속되어 유실되지 않습니다.
3. **공개 입력 실행 후 회전하면 "결과 내보내기"가 "먼저 실행하세요"로 거부된다.**
   → 실행 결과는 인메모리라 재실행이 필요합니다. 재실행은 새 runId로 증거를 새로 만들므로 자기일관성이 유지됩니다.
4. **탭 직후 강제 kill 시 UI 순번(prefs apply)이 원장(commit)보다 뒤처질 수 있다.**
   → 수십 ms 창에서 이벤트 ID 재사용이 가능하지만, core의 중복 방어(REPLAY 멱등·행동 원장)가 이를 흡수합니다 — 오히려 선언한 exactly-once 기능이 동작하는 사례입니다.
5. **첫 권한 허용에도 "다시 허용되었습니다" 문구가 뜬다.**
   → 권한 상태 전이를 같은 문구로 알리는 설계이며 가이드에 명시했습니다.
6. **중단된 약의 체크리스트 사유가 "기록 없음 또는 중단·만료"로 표시된다(만료+잔량 보유는 "지시 없음(중단·만료)").**
   → 중단(REVOKE)은 그 약의 잔량 기억도 같은 scope라 함께 무효화되어 유효 집합이 비기 때문입니다. 두 문구 모두 가이드 §4에 문서화했습니다.
7. **runProbeSteps 실패 시 stale run에 abort가 기록될 수 있는 잠재 결함.**
   → import 시점에 파싱을 먼저 통과시키므로 실제 발현 경로가 사실상 없고, 영향도 UI 리허설용 prefs 2키에 국한됩니다. 알고 있으며 동결 유지가 옳다고 판단했습니다.

## B. 핵심 문답 (구현 소유 증명)

1. **Q. Signature mechanism을 한 문장으로.**
   기억마다 {유형, 유효조건(약별 지시 버전·기한·중단 scope·권한), 출처 링크, tombstone}을 기록하고, 재사용·충돌·복구 세 지점이 하나의 유효성 판정을 공유하는 원장입니다 (ChebiCore.kt).
2. **Q. claim-off는 어떻게 끄나? 별도 APK 아닌가?**
   같은 APK, `ChebiCore` 생성자 인자 `gateEnabled=false` 하나입니다. off도 허수아비가 아니라 '살아있는 기억 통짜 재사용 + 충돌 시 전체 무효화(과잉 복구)'로 전 episode를 정상 완주합니다. 짝비교는 격리 namespace 2개(`medkeeper-cmp-full/off`)에 같은 시작 상태를 복제하고 같은 이벤트 열을 넣습니다 (MedDomain.kt MedComparisonLab).
3. **Q. 공개 UI와 protected 경로가 같은 코어라는 증거는?**
   ①UI 버튼이 합성 이벤트를 만들어 Probe와 같은 `core.execute()`로 들어감(MedDomain.emit) ②`SameAdapterPathTest`(소스 스캔+행동 동치) ③실측: 공식 Runner 13-step과 공개 UI 13-step의 **step 1~8 상태 해시가 바이트 동일**, decision·selected 13/13 동일 — 차이는 KILL 단계의 process_epoch(공식 harness만 실제 kill)뿐입니다.
4. **Q. 해시 체인이 KILL을 넘어 이어지는 이유는?**
   before 해시를 epoch 갱신 이전에 찍어 직전 after와 항상 일치시키고, epoch 증가는 그 step의 변화로 기록합니다 (ChebiCore.execute 상단 주석).
5. **Q. 왜 권위가 약별 map인가?**
   전역 권위면 항생제 정정이 혈압약 기억까지 기각합니다. `authorities[entity]`로 두고 isValid·정정·OOO 기각이 전부 entity 기준입니다 (CORE-2 영향 특정).
6. **Q. 도착 기억이 권위 중립("")인 이유는?**
   도착은 지시가 아니라 일어난 사건이므로, 지시 정정이 도착 이력을 무효화하면 안 됩니다. 잔량·임계도 같은 원칙으로 분리 등록됩니다.
7. **Q. 기한만 정정(UNTIL-only)의 의미론은?**
   "값이 오면 기한을 승계, 기한이 오면 값을 승계." 같은 step의 권위 정정 동반 시 방금 무효화된 기한 보유 기억을 새 권위로 인수 재기록, 기한 보유 기억이 전무하면 기한 없는 TERM에 신규 부여. claim-off 팔에는 이 정밀 인수를 주지 않아 A/B 대비를 보존합니다 (upsertCorrection).
8. **Q. exactly-once는 어떻게?**
   결정=PROPOSED(draft), 결과 도착=commit 경계(COMMITTED), 취소=CANCELLED. 재전달은 새 행동을 만들지 않고 동일 action을 echo하며 라벨은 원장 상태와 1:1(PENDING/CONFIRMED_COMPLETE/ABSTAIN). WAIT 보류 재전달은 원본 이벤트 ID로 정확히 1회 재시도.
9. **Q. 삭제 부활 차단과 재학습 허용의 경계는?**
   시스템 경로(out-of-order 재전달)의 부활은 tombstone 게이트가 `REJECTED_TOMBSTONED`로 기각(상태 무변형). 사용자의 명시적 재학습(정규 UPSERT)은 새 출처의 새 기억으로 허용 — 부활이 아닙니다. 재학습 사이클의 새 지연 결과 도착도 정상 반영됩니다.
10. **Q. 오프라인에서 무엇이 멈추고 무엇이 계속되나?**
    로컬 판단(체크리스트 확정·복용 기록·잔량 감산)은 계속, 전송 성격 결정(리필 draft)만 정직한 WAIT. 회복 후 재전달 1회 재시도 (선언 모바일 절).
11. **Q. 프리필 지표가 두 개인 이유는?**
    화면 지표(슬롯 등재 행+이번 세션 도착 반영, evidence/ui/metrics.json)와 비교 리포트 지표(결정 게이트 selected 크기, s3/s7)는 정의가 다릅니다 — 기술노트 §3.3에 구분 명시.
12. **Q. 결정론의 근거는?**
    AI model·backend 없음, 시간은 가상시계, digest는 process_marker 제외 canonical JSON — 같은 입력이면 기기·프로세스 이력과 무관하게 같은 해시 체인. 릴리즈 빌드는 동일 환경 재빌드 시 APK sha 동일 확인.
13. **Q. 의료 가드의 경계는?**
    기억·대조·표시까지. 용량·복용 여부 결정 없음, 복용은 최종확인 이벤트로만, 전부 합성 — 선언·화면·코드 주석·문서 4곳 동일 문면.
14. **Q. 감사는 얼마나 했나?**
    자체 감사 6라운드(발견 33→16→46→21→19+2→7LOW), 각 라운드 수정 후 단위 43종·공식 Runner 5팩(13-step+자체 미지표면 4종)·FINALIZE/VALIDATE·UI 자동 실기 35항목 전체 재검증. 마지막 라운드는 실질 조치 0건으로 수렴.
15. **Q. 데모와 실제 판정이 다르면?**
    데모 영상 시나리오는 UI 자동 실기와 동일 순서라 재현 가능하고, 모든 화면 관찰은 evidence export와 같은 상태의 두 표현입니다 — 임의 시점 대조를 환영합니다.
